Working notes for Claude Code. The plan is in `HANDOFF.md`; read it first.

## Project
An R/Shiny dashboard for looking up maize genes and seeing how their expression changes under cold (chilling and freezing) across published RNA-seq studies, with results pooled across studies by tissue, contrast type, growth system and other factors. Owner: Rubén Rellán-Álvarez (GEMMA Lab, NC State).

Sibling of **MaizExpressN** (nitrogen): `/Users/rra/Documents/MaizExpressN`, https://github.com/sawers-rellan-labs/MaizExpressN, live app https://01a155ac-51db-275e-103a-4c139985dd6d.share.connect.posit.cloud/. This project was created from its infrastructure on 20 Oct 2026; its CLAUDE.md holds the full history behind every inherited decision.

## Conventions
- Primary gene key: B73 RefGen_v5 gene IDs (`Zm00001eb…`); v4/v3 IDs, symbols and Arabidopsis names are search aliases. `annotation/` was copied from MaizExpressN (same gene models Zm00001eb.1); rebuild only if the sources change.
- Study key: `study_id` (FirstAuthorYear) from the catalogue.
- Effect sign (proposed, confirm at the contrasts checkpoint): log2FC = log2(cold / control temperature), so positive means higher under cold. Recovery contrasts: log2(recovered / still cold) or vs control, to decide at M4. The app has a toggle to flip the sign.
- Never pool counts across studies; pool effect sizes (log2FC with SE) only.
- R for analysis and the app (renv; `renv.lock` copied from MaizExpressN, R 4.5.3). Heavy processing runs on NC State's Hazel cluster (Slurm); only gene tables and Parquet results come back to the Mac.

## Rules inherited from MaizExpressN (apply here unless Rubén says otherwise)

- Public-facing files (app, public repo, Methods) list only the studies used in the analysis and never say why a study was not used; library QC exclusions are not reported per study. Reasons and evidence go in `private/` (gitignored). In code: `NOT_USED` in `build_runs.py` says only "not used in this analysis".

## Inherited facts and lessons from MaizExpressN (Hazel, pipeline, analysis, app)
Paths and study names below refer to MaizExpressN; the same setup applies here.

- Scheduler: Hazel moved to **Slurm** on 17 Aug 2026; LSF retires end of Fall 2026 (hpc.ncsu.edu). HANDOFF's LSF notes are superseded.
- Workflow (16 Oct 2026, see `pipeline/README.md`): our own MD5-checked downloader (`download_fastq.sh`, fed from runs.tsv; handles CNCB GSA) + nf-core/rnaseq 3.27.0 (fallback 3.24.0) in salmon mode with the official nf-core `hazel` profile and `pipeline/conf/maizexpressn.config`. One Nextflow head job per study (`run_study.sh`, sbatch); first run builds and saves the decoy-aware salmon index for reuse.
- Slurm on Hazel (`slurm_check.txt`, 16 Oct 2026): account `maize_cpu`. Partitions: `compute` (default; QoS `normal` 4 d / 256 CPUs per job, `long` 10 d / 128 CPUs), `compute_partners` (QoS `p_maize` 32 CPUs, `short` 2 h), `xfer` (data-transfer node servxfer; QoS `xfer`, 4 CPUs, 24 GB, 4 d), GPU partitions unused. Interactive jobs need `--qos=short`. Downloads run as `download_study.sbatch` on `xfer`. Only `nextflow/25` is in the default module path (BRC's 26.04.3 isn't); BRC container library has salmon 1.10.3, fastqc, multiqc, gffread, tximeta. `net_check/` (16 Oct 2026): compute nodes have **no internet**; the `xfer` node (servxfer) does and can run sbatch. So downloads and Nextflow head jobs run on `xfer` (QoS cap 4 CPUs / 24 GB per user: 2-CPU jobs, two at a time); pipeline steps run on `compute`. Hazel's nextflow/25 module is 25.10.3; `run_study.sh` pins `NXF_VER=25.10.8` so nf-core/rnaseq 3.27.0 can run.
- Hazel facts (`hazel_check.txt`, 16 Oct 2026): modules nextflow/25, apptainer/1.4.2-1, java/17, conda/26.3.2; LSF 10.1. Login nodes reach ENA (HTTPS and FTP-over-HTTPS), NCBI, AWS SRA ODP, CNCB GSA (HTTPS fast, FTP slow), MaizeGDB, GitHub, Docker Hub and the Galaxy Singularity depot. Not yet tested: internet from compute nodes, and which LSF queues rrellan may use. `/usr/local/usrapps/maize` is shared by several lab members and file-quota limited: no conda environments there. `/share/maize` (-> /gpfs_common/share01/maize, 120 T free) is the GPFS scratch candidate for Nextflow work dirs.
- First quantification (Mu2017, 16 Oct 2026): COMPLETED. 74-86% of 17-18 M read pairs mapped (salmon, decoy-aware), library IU, 39,090 genes; positive control OK (nnr1, nii1, gln2 down under LN; gln4/5, asn1 up). Reference bundle with salmon index saved at `/share/maize/rrellan/MaizExpressN/reference/nfcore_genome` (15 GB) and reused by later runs. Lessons now in the pipeline: batch shells need `source /etc/profile.d/modules.sh`; the head job must `module load singularity` (it pulls images missing from the BRC library); keep nf-core's default `gtf_extra_attributes` (empty breaks tximport); right-size MAKE_TRANSCRIPTS_FASTA and run SALMON_INDEX on `compute_partners`/`p_maize` (the 72 GB default waited ~11 h). Salmon quant takes 20-55 min per ~18 M-pair sample on 6 CPUs and uses ~10 GB of its 36 GB request.
- Download fix (17 Oct 2026): 10 of the first 27 download jobs failed MD5 on a few files each. Cause: `curl --retry` with `-C -` (curl 7.76.1 on Hazel) can resume from a stale offset and duplicate bytes when connections drop (frequent at 8 connections per job). `download_fastq.sh` now runs its own resume loop (no `--retry`, stall detection), re-downloads from scratch on MD5 mismatch, and defaults to 6 connections. Failed studies were resubmitted; verified files are skipped. Second fix (17 Oct 2026): CNCB GSA closes transfers every few hundred MB. The old loop gave up after 8 resumes, logged MD5_MISMATCH and deleted the partial file, so 2 GB files never finished (Guo2023: 4 files). Now each round allows 40 resumes and keeps an unfinished `.part` (logged INCOMPLETE). Only a file that curl finished and that fails its MD5 is deleted. Jia2023 and Li2025 had started before this fix and kept losing files, so they were restarted at 19:40 on 17 Oct and their head jobs re-pointed to the new download jobs.
- xfer QoS limits per user: 4 jobs, 4 CPUs, 24 GB. Head jobs use 1 CPU / 12 GB; downloads 1 CPU / 4 GB. Queued downloads run at Nice 20000 so head jobs get freed slots (age priority beat Nice 500). `scontrol update NumCPUs` does not lower a pending job's cpus-per-task: resubmit instead.
- Compute queue (18 Oct 2026): `compute` nodes are shared with partner groups' jobs and can fill up overnight (tasks pending on Priority for 8+ h). Do NOT move Nextflow task jobs to another partition with `scontrol update Partition=compute_partners QOS=p_maize`: Nextflow polls `squeue -p <its queue>`, so a moved job vanishes from its view and any task running longer than ~5 min is declared 'terminated by the external system' even though it finished (Buzzicotti2026 failed this way on 18 Oct; tried with an automatic mover, now removed). If overnight waits become a problem, route processes to compute_partners/p_maize in the config instead (32 CPUs per user).

- M2 sample-sheet conventions (spec in `metadata/build/curation_spec.md`):
  - N_amount is the amount of N itself: `mM N` for solutions (Ca(NO3)2 counts twice), `kg N/ha` for field rates (urea at 46% N).
  - phase is what happened to the sample's own N supply at time 0 (steady / starvation / resupply); time_h is set for every sample of a time-resolved design, controls included, so contrasts can be time-matched.
  - Libraries shared between studies are curated once under the owning study (`runs.tsv` study_id; `also_used_by` names the borrower). Contrasts may borrow them; pooling counts them once.
  - Run exclusions live in `metadata/build/build_runs.py` with a reason per run; sample-level exclusions in the sample sheet's include/curation_note.
